# V0.9.2 手工验收清单

## A. 部署与迁移

- [ ] 升级前备份代码、数据库和 `.env`。
- [ ] 当前版本为 `a4d7c92f5e10`，只有一个 Alembic head。
- [ ] 执行 `alembic upgrade head` 后版本为 `b5f2c4a9d703`。
- [ ] `alembic check` 无待迁移结构差异。
- [ ] 原有边与导入批次的记录数、active 状态、scope_key、payload_hash 保持不变。

## B. Scope 内外身份隔离

- [ ] 同一项目、同一来源系统、同一 source_ref，在 `dag:orders` 与 `dag:customers` 两个 scope 各导入一条边，数据库保留两条不同边。
- [ ] 两个 scope 使用同样的 run_id，且 payload 不同，作为两个逻辑批次分别成功。
- [ ] 在 `dag:orders` 导入空的 `full_snapshot` 且 `complete_scan=true`，只停用 orders scope 的旧边；customers scope 同名边保持 active。
- [ ] 同一 scope、同一 source_ref 出现在同批两次时，整批报错，不修改已有边。
- [ ] 同一 scope + run_id 的成功批次以相同 payload 重放，返回 `replayed=true`；同 ID 不同 payload 返回 409。

## C. V0.9.1 导入保护回归

- [ ] `incremental` 不允许 `complete_scan=true`。
- [ ] `incremental` 必须至少有一条边。
- [ ] `full_snapshot` 必须设置 `complete_scan=true` 且显式使用非 `default` scope。
- [ ] `preview` 返回 `writes_performed=false`，不会写入边、批次或活动事件。
- [ ] `full_snapshot` 中任一边校验失败，现有边不会被部分停用。
- [ ] 失败导入形成失败批次记录，保留失败次数与错误摘要；修正元数据后用相同 payload 重试成功。
- [ ] `stale-candidates` 只返回候选，不自动停用边。
- [ ] 健康度按 `source_system + scope_key` 分组，并能查看最近成功/失败批次。

## D. 路径查询限制

- [ ] 默认 max_depth=20 可以得到普通路径结果。
- [ ] 对超过当前最大深度的路径，返回 `found=false, truncated=true, reason=MAX_DEPTH_REACHED`。
- [ ] 把最大深度调大后，可查询到路径；无法连接时返回 `truncated=false, reason=NO_PATH`。
- [ ] max_depth=0 或 51 返回 422。
- [ ] 前端有最大路径深度输入，能提示“深度不足”和“无路径”的区别。

## E. Graph / UI

- [ ] lineage graph 显示来源和 scope，且能区分当前 active 与 inactive 边。
- [ ] 导入批次表显示 scope、模式、停用数、attempt_count、failure_count 和错误摘要。
- [ ] 前端“只读预检”“来源健康度刷新”“查看过期候选”按钮可用。

## F. 回退保护

- [ ] 在副本中创建同 source_ref 跨 scope 数据后，尝试 downgrade 会中止并给出冲突提示。
- [ ] 未出现跨 scope 重复数据时，downgrade/upgrade 演练可按团队迁移规程完成。
