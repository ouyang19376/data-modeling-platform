# V0.9.1 → V0.9.2 升级指南

## 1. 适用范围

适用于已升级到 V0.9.1、数据库 revision 为 `a4d7c92f5e10` 的参考工程。V0.9.2 只调整两个唯一约束和相应 upsert/幂等查询，以支持同一来源系统在不同 `scope_key` 中使用局部唯一的 `source_ref` 和 `run_id`。

**版本路径提醒：** 如果当前 revision 是 V0.9 的 `9bf3e67a1d52`，请先按 `docs/UPGRADE_GUIDE_V091.md` 完成 V0.9.1 的增量迁移，再执行本指南；如果当前是 V0.8 的 `4a8fc21d0e63`，请使用完整工程包中的 V0.9 和 V0.9.1 迁移链，勿直接套用本最小补丁。

## 2. 升级前检查

1. 停止应用服务。
2. 备份数据库和代码，推荐使用数据库副本先演练。
3. 检查迁移状态：

   ```bash
   python -m alembic current
   python -m alembic heads
   ```

4. 预期当前 revision 是 `a4d7c92f5e10`，且只有一个 head。若版本不同、存在多个 head 或本地模型有未提交自定义，不应直接继续。
5. 审核并保存 `docs/V0.9.2_LINEAGE_SCOPE_IDENTITY.md` 中的唯一键变更说明。

## 3. 合并和迁移

解压最小补丁到临时目录，比较并合并以下文件，不要覆盖本地 `.env`：

- `backend/app/models.py`
- `backend/app/main.py`
- `backend/app/config.py`
- `.env.example`
- `frontend/static/index.html`、`frontend/static/app.js`、`frontend/static/app.css`（图谱最大路径深度输入与截断反馈）
- `migrations/versions/b5f2c4a9d703_scope_aware_lineage_identity_v092.py`
- `tests/test_api.py`（供差异检查与回归用，不建议无条件覆盖本地测试）
- `docs/` 中 V0.9.2 对应的契约与验收文件

在与应用相同的 Python 环境和 `DATABASE_URL` 下执行：

```bash
python -m alembic upgrade head
python -m alembic current
python -m alembic check
pytest -q
node --check frontend/static/app.js
python -m compileall -q backend migrations tests
```

预期目标 revision：`b5f2c4a9d703`。测试参考结果：35 项通过。

## 4. 升级后的关键验收

1. 相同 source_system、相同 source_ref、不同 scope 的两条边能同时存在。
2. 相同 source_system、相同 run_id、不同 scope 的两个批次能分别保存。
3. 在一个 scope 上执行空的显式完整快照，只会停用该 scope 内的边；其他 scope 的同名边保持 active。
4. 在同一个 scope 内重复 source_ref 仍会使整批失败。
5. 同一 scope + run_id 的成功批次同 payload 重放返回 200；同 ID 不同 payload 返回 409。
6. 普通增量批次、只读预检和过期候选查询不会更改边的 active 状态。
7. 路径查询默认 max_depth=20，限制在 1–50；当搜索边界被触及时，应返回 `truncated=true` 而不是把深度不足误报为无路径。

## 5. 回退

V0.9.2 → V0.9.1 回退时，如果存在跨 scope 重复的 `source_ref` 或 `run_id`，迁移会故意拒绝降级，因为旧版唯一键无法表达这些记录。先备份，运行降级演练并按报错样例处理重复引用后，再考虑：

```bash
python -m alembic downgrade a4d7c92f5e10
```

不要只回滚应用代码而保留不兼容数据库结构。线上环境不得未经变更评审执行降级。
