## 本版决策摘要

身份模型最小化：一个 `users` 表同时表达人与服务账号（`kind` 区分），API Key 只存 SHA-256 哈希，secret 仅在创建响应返回一次；授权落在 `project_members`（owner/editor/viewer 三角色），不做组织树与多租户层级。

生产启动门禁从"一律拒绝"改为"配置放行"：`AUTH_MODE=demo`（默认，仅 local/dev/test）保持 V0.9.2 行为（`X-Actor` 演示身份）；`AUTH_MODE=api_key` 才允许 `APP_ENV=production/staging` 启动，且必须 Bearer 认证。

第一个连接器选 dbt manifest：文件驱动、离线可测、无外部服务依赖；只导入模型级依赖边（`parent_map`），复用 V0.9.2 已验证的导入事务、幂等与 scope 身份，不新建边存储语义。

发布评审上下文是"汇总"而非"新存储"：`GET /api/models/{id}/review-context` 复用既有 diff/impact/图谱逻辑只读计算，`submit-review` 把摘要写进活动事件作为评审证据，不新增评审表。

full_snapshot 停用增加可配置比例门槛（默认 0.5）：超阈值必须显式 `confirm_deactivation=true`，空完整扫描天然落入门槛；preview 提前告知比例，不让调用方布尔参数单独决定大规模删除。

契约冻结：V1.0 起 OpenAPI 只允许附加式演进（新增端点、新增可选字段、新增枚举值需评审记录）；破坏性变更一律走 V2.0。这是选 V1.0 而非 V0.10 的核心理由之一。

# 01 版本定位与建设目标

## 1.1 为什么是 V1.0（版本号论证）

V0.x 系列（MVP → V0.6 → V0.7 → V0.8 → V0.9/9.1/9.2）的使命是**把 README 开头定义的纵向闭环补齐**：业务调研 → 模型设计 → 规范校验 → 评审发布 → 版本差异 → DDL 预览，外加 V0.9 的血缘方向（图谱快照、四视图、最短路径、外部血缘导入族）。截至 V0.9.2，这些目标均已交付且有 111 个自动化测试佐证（`tests/test_api.py`，README.md:44-57）。V0.x 已收官，继续编号为 V0.10 会误导市场与团队对版本性质的判断。

选择 V1.0 的三个理由：

1. **变更性质是破坏性的**。V1.0 替换身份模型（`X-Actor` 演示头 → Bearer API Key，`backend/app/main.py:115-120` 的 `resolve_actor` 将被认证主体取代）、改变生产启动门禁（`backend/app/config.py:51-64` 的 `validate_startup` 从"production 一律拒绝"改为"AUTH_MODE 放行"）、改变 full_snapshot 停用行为（新增确认门槛）。按语义化版本理念，身份与门禁的破坏性变更需要主版本号，而不是补丁号。

2. **V1.0 = 契约冻结**。正式版的第一职责是稳定契约：55 个既有端点冻结为 1.0 契约，此后只增不改（附加式演进政策见第 8.4 节）。V0.10 这个编号表达不了"冻结"这层含义。

3. **上一版设计文档已指明方向**。`docs/v0.9/_extracted_spec.md:749-759` 的"建议下一版 V1.0 的范围"明确列出：完成一个真实连接器、固化连接器合同、评审页面集成影响分析与历史图谱 diff、生产化安全门禁。V1.0 的范围与该建议一一对应，保持文档承诺的连续性。

V0.9.1/9.2 已经示范了版本号的分工：补丁式修订（x.y.z）用于治理增补，主版本（V1.0）用于质变。V1.0 的本质是**从"功能可用的参考实现"转变为"可交付、可授权、可接入的正式版"**。

## 1.3 本版目标

1. **安全门禁**：以 API Key 为最小可行认证，项目级三角色授权，生产环境从"拒绝启动"转为"配置放行"；审计覆盖认证失败与授权拒绝。
2. **连接器生态第一步**：内置 dbt manifest 参考连接器，把真实世界的模型依赖以 V0.9.2 已验证的幂等事务写入外部血缘；同时固化连接器合同（映射规则、scope 规则、失败语义）。
3. **评审闭环增强**：发布前一处看全变更摘要、候选影响、图谱差异与血缘覆盖盲区；评审摘要进入事件流作为证据。
4. **血缘停用治理**：full_snapshot 大规模停用必须人工确认，preview 提前披露比例。
5. **可观测生产化**：`/metrics` 增加业务指标族，`/api/observability/summary` 增加血缘与认证摘要，lineage health 改 SQL 聚合（契约不变）。
6. **契约冻结**：65 个端点冻结为 V1.0 契约，附加式演进政策成文。

## 3.2 身份与授权模型

三个实体，最小化：

| 实体 | 职责 | 关键设计 |
| --- | --- | --- |
| `users` | 认证主体：人或服务账号 | `kind=human/service_account`；`user_key` 全局唯一（如 `u:alice`、`sa:dbt-importer`）；`auth_source` 为 OIDC 预留 |
| `api_keys` | 凭据 | `key_id` 公开、`key_hash=SHA-256(secret)`；secret 仅创建响应返回一次；支持吊销与过期；`last_used_at` 节流更新 |
| `project_members` | 授权 | (project, user) 唯一；角色 owner/editor/viewer；平台 admin（`is_admin`）绕过项目成员检查 |

**令牌格式**：`Authorization: Bearer dmc_<key_id>_<secret>`。`key_id` 模式 `^[A-Za-z0-9]{10,40}$`（不含下划线，保证切分无歧义）；secret 为 256 位随机数 base64url（43 字符）。服务端以 `hmac.compare_digest` 常量时间比较哈希。

**启动门禁**（改写 `backend/app/config.py:51-64` 的 `validate_startup`）：

| AUTH_MODE | APP_ENV | 行为 |
| --- | --- | --- |
| `demo`（默认） | local/dev/development/test | 放行；`X-Actor` 生效，身份恒为内置演示管理员；启动日志提示非生产模式 |
| `demo` | production/staging | 拒绝启动（与 V0.9.2 一致的安全默认） |
| `api_key` | 任意允许环境 | 放行；必须 Bearer；`X-Actor` 忽略；production 允许但启动时校验 `DATABASE_URL` 非 sqlite 时仅警告（记录 WARN 日志），HTTPS 终止由网关负责（部署要求） |
| `api_key` | 其他未知环境 | 拒绝启动 |

**Bootstrap（鸡生蛋问题）**：`api_key` 模式首次启动且 `users` 为空时，允许 `POST /api/auth/bootstrap`（需环境变量 `BOOTSTRAP_TOKEN`）创建首个管理员并返回其密钥；`BOOTSTRAP_TOKEN` 未配置返回 409 `BOOTSTRAP_NOT_CONFIGURED`；`users` 非空后该端点永久 409 `BOOTSTRAP_ALREADY_DONE`。

## 4.1 M1 认证与 API Key 管理

**用户故事**：作为平台管理员，我可以在不改造前端交互模式的前提下，用一枚可轮换的 API Key 让连接器和 CI 安全地调用平台；作为普通成员，我只能管理自己的密钥。

### 4.1.1 API 契约

**POST /api/auth/api-keys**（创建密钥）

- 认证：Bearer（本人）。
- 请求：

```json
{
  "name": "dbt-importer-key",
  "expires_in_days": 90
}
```

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| name | string | 1-80 | 用途备注，仅展示 |
| expires_in_days | integer | 可选，1-3650 | 缺省不过期 |

- 响应 201：

```json
{
  "key_id": "ak_7f3d9c2a1b",
  "secret": "dmc_ak_7f3d9c2a1b_<43位base64url>",
  "name": "dbt-importer-key",
  "status": "active",
  "created_at": "2026-10-27T10:00:00+00:00",
  "expires_at": "2027-01-25T10:00:00+00:00"
}
```

`secret` 仅在本次响应返回；服务端只存 `key_hash`。响应体不含 hash。

- 错误码：401 `AUTH_REQUIRED`（缺省/非法令牌）、422 `REQUEST_VALIDATION_FAILED`。

**GET /api/auth/api-keys**（列出本人密钥）

- 响应 200：`[{"key_id","name","status","created_at","last_used_at","expires_at"}]`（不含 secret/hash）。admin 可用 `?user_key=` 查他人（审计记录）。

**POST /api/auth/api-keys/{key_id}/revoke**（吊销，幂等）

- 响应 200：`{"key_id":"ak_...","status":"revoked"}`；重复吊销返回 200（幂等）。
- 错误码：404 `API_KEY_NOT_FOUND`（不存在或不属于本人且非 admin）。

**GET /api/auth/me**（当前身份）

- 响应 200：

```json
{
  "user_key": "sa:dbt-importer",
  "display_name": "dbt 导入服务账号",
  "kind": "service_account",
  "auth_mode": "api_key",
  "is_admin": false,
  "projects": [{"project_id": 1, "project_key": "PRJ_RETAIL", "name": "零售数据平台试点", "role": "editor"}]
}
```

**POST /api/auth/bootstrap**（一次性引导，仅 api_key 模式）

- 请求：`{"bootstrap_token": "...", "user_key": "u:admin", "display_name": "平台管理员"}`。
- 响应 201：`{"user_key":"u:admin","key_id":"ak_...","secret":"dmc_..."}`。
- 错误码：409 `BOOTSTRAP_NOT_CONFIGURED`（未设 `BOOTSTRAP_TOKEN`）、401 `BOOTSTRAP_TOKEN_INVALID`、409 `BOOTSTRAP_ALREADY_DONE`（users 非空）、422 `REQUEST_VALIDATION_FAILED`。

### 4.1.2 数据模型变更

新增 `users`、`api_keys` 两表（字段见第 5.1 节）。无既有表变更。

### 4.1.3 迁移影响

纯附加：新 revision 建两表；downgrade 删除两表（密钥数据丢失，回滚前须导出并轮换，见第 8 章）。

### 4.1.4 验收标准

- 自动化：创建→响应含 secret 且仅此一次；用 secret 调用受保护端点 200；错误 secret 401；吊销后 401；过期密钥 401；bootstrap 三种错误分支；demo 模式下 `X-Actor` 仍可用。
- 手工：按验收清单 B 节逐项执行。

## 4.3 M3 dbt manifest 参考连接器

**用户故事**：作为数据开发，我把 dbt 项目的 `manifest.json` 导入平台，模型间的依赖立即以外部血缘呈现（`lineage_type=dbt_dependency`），与人工设计关系分域对照，重复导入不会产生重复边。

### 4.3.1 连接器合同（固化）

| 合同项 | 规则 |
| --- | --- |
| 入口 | `POST /api/projects/{id}/lineage/import/dbt-manifest`（JSON body，manifest 作为对象字段，不做 multipart） |
| 解析范围 | `manifest.nodes` 中 `resource_type == "model"`；`manifest.sources` 全量；忽略 test/seed/analysis/snapshot/operation/exposure |
| 模型键映射 | dbt 对象 → 平台 `model_key`：model 节点取 `name`；source 节点取 `name`（源表名）。平台必须先以相同 `model_key` 登记模型（建议 ODS 模型按 dbt 源表命名） |
| 依赖推导 | 对每个节点 N，取 `manifest.parent_map[N.unique_id]` 中的父节点 P（仅 model/source 类）；每条 (P→N) 产生一条边 |
| 边身份 | `source_ref = "dbt:{P.unique_id}=>{N.unique_id}"`（manifest 内稳定，支持 upsert 与幂等重放） |
| scope 规则 | `scope_key` 缺省 `"dbt:" + metadata.project_name`；同项目多 dbt 项目用不同 scope 隔离（与 V0.9.2 scope 语义一致，`models.py:444-446`） |
| 血缘属性 | `lineage_type="dbt_dependency"`、`transformation_type="sql"`、`confidence=100`、`job_key="dbt:{project_name}"` |
| 边元数据 | `metadata` 仅放：`dbt_schema_version`、`project_name`、`node_materialized`、`node_database`、`node_schema`、`node_alias`（≤50 键 / 8000 字节，复用既有校验，`main.py:3611-3626`） |
| 写入语义 | 强制 `scan_mode=incremental`、`complete_scan=false`（不停用任何边）；复用 `_plan_lineage_import`（`main.py:3503`）与导入事务（`main.py:3717`） |
| 幂等 | `run_id` 缺省 `"dbt-manifest:{scope_key}:{received_at ISO}"`；同 run_id 同 payload 重放 200 `replayed=true`，不同 payload 409 `LINEAGE_RUN_ID_REUSED`（与 V0.9.2 一致） |
| 规模上限 | manifest 序列化后 ≤ 8 MiB（配置 `DBT_MANIFEST_MAX_BYTES`）；推导边数 ≤ 1000（超出返回 `DBT_MANIFEST_TOO_LARGE`，提示按 scope/文件夹拆批） |
| 未匹配处置 | 缺省整批拒绝（422 `DBT_NODES_UNMATCHED`，`details.unmatched_sample` 最多 50 个唯一 ID）；`skip_unmatched=true` 时跳过并计入响应 `skipped_unmatched`，跳过明细写入 run 的 `result_json` |

## 4.5 M5 full_snapshot 停用人工确认

**用户故事**：作为治理人员，连接器一次空扫描或配置错误不应悄悄停用大量血缘边；超过比例的停用必须显式确认，且我能提前通过 preview 看到比例。

### 4.5.1 契约变更（附加）

`ExternalLineageImport`（`backend/app/schemas.py:196-207`）新增可选字段：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| confirm_deactivation | boolean | false | full_snapshot 计划停用比例超阈值时必须为 true |

服务端行为（改写 `main.py:3803-3827` 的 full_snapshot 分支，在任何写入前计算）：

```
planned = 计划停用的 active 旧边数（同 scope 未出现在本批）
active_total = 该 scope 现有 active 边数
ratio = planned / max(1, active_total)
if ratio > FULL_SNAPSHOT_DEACTIVATE_RATIO_THRESHOLD and not confirm_deactivation:
    422 LINEAGE_DEACTIVATION_CONFIRM_REQUIRED
    details = {planned_deactivated, active_existing, ratio, threshold, scope_key}
```

- 阈值配置：`FULL_SNAPSHOT_DEACTIVATE_RATIO_THRESHOLD`（0.0-1.0，默认 0.5）。

# 10 风险登记与处理策略

| 风险 | 影响 | V1.0 处理 | 后续动作 |
| --- | --- | --- | --- |
| 每请求查密钥带来开销 | 认证路径延迟 | 进程内密钥缓存（TTL 60s）+ last_used_at 节流写； revoked 延迟 ≤ TTL 并文档化 | 压测后评估 Redis/本地 TTL 调优 |
| 授权遗漏端点 | 越权访问 | 授权矩阵成文（3.3）+ 每端点类 403 自动化用例 + 上线前矩阵走查 | 契约测试持续门禁 |
| bootstrap 令牌泄露 | 首管理员被冒建 | 一次性、引导后关闭、建议引导完立即吊销并轮换 | 审计事件覆盖 |
| dbt manifest 版本差异 | 解析失败或漏边 | 只用 nodes/sources/parent_map/metadata 稳定字段；结构不符显式 422 | 跟踪 dbt schema 版本演进 |
| model_key 匹配过严 | 导入整批拒绝 | skip_unmatched 选项 + 接入指南（先按 dbt 命名登记 ODS） | 连接器配置化映射规则（P2） |
| 停用阈值误伤合法大扫描 | 连接器流程中断 | 可配置阈值 + preview 预告 + 显式确认 + run 记录 | 按来源分级阈值（P1） |
| 指标标签基数爆炸 | Prometheus 性能 | 禁用 project_key/model_key 标签 | 压测验证 |
| main.py 单体继续膨胀 | 维护成本 | 允许内拆模块（auth/lineage/review），契约回归测试保护 | 前端产品化时同步重构（P2） |
| 密钥哈希库泄露 | 凭据伪造 | SHA-256 + 高熵 secret（256 位）+ 常量时间比较；不明文存储 | 评估 HMAC  pepper（P1） |
