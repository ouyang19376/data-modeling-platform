# V1.0 验证报告与交付边界

> 本报告为**设计层面**的可行性与影响面分析（评审基线）。标注「待开发后填写」的条目在实现完成、测试与手工验收执行后回填实测值。

## 1. 设计可行性结论

| 维度 | 结论 | 依据 |
| --- | --- | --- |
| 契约可行性 | 可行 | 全部新增/变更端点均落在既有代码结构的可复用点上：导入事务（`backend/app/main.py:3717`）、图谱 diff（`main.py:2147`）、影响分析（`main.py:2552`）、变更摘要（`main.py:2361`）、校验（`main.py:605`）均为纯函数或可组合逻辑，review-context 为只读汇总，无新存储语义 |
| 数据模型可行性 | 可行 | 3 张新表 + 1 列均为附加式变更，不触碰既有 15 张表的列定义；`lineage_import_runs` 加列与 V0.9.1 加列（`a4d7c92f5e10`）模式一致 |
| 迁移可行性 | 可行 | Alembic 链式追加（down_revision=`b5f2c4a9d703`）；SQLite 用 batch 模式、PostgreSQL 用普通 ALTER 的双路径在既有迁移中已有先例（`b5f2c4a9d703`） |
| 安全模型可行性 | 可行（最小化） | API Key + 三角色不引入新依赖（哈希用标准库 hashlib/hmac）；认证失败 fail-closed；demo 模式显式保留开发体验 |
| 连接器可行性 | 可行 | dbt manifest 的 `nodes`/`sources`/`parent_map`/`metadata` 是跨 schema 版本（v10-v12）稳定的字段子集；解析失败显式 422，不静默丢边 |
| 性能影响面 | 低-中 | 新增每请求一次密钥查询（缓存 TTL 60s 缓解）；health 改 SQL 聚合为净改善；指标 gauge 抓取时求和仅限 MVP 规模 |
| 前端影响面 | 中 | app.js 约 2396 行，需新增 4 个面板（密钥/成员/评审上下文/dbt 导入）；沿用既有 modal/toast/api 工具函数（`app.js:82-160`），无框架变化 |

## 4. 设计层面已验证（静态核对）

- 新端点路径与既有路由命名风格一致（`/api/...` 前缀、复数资源、路径参数 `{id}`）；与 README.md:112-133 的端点一览无命名冲突。
- 新增错误码与既有错误体封装一致（`{"error": {code,message,details}, "request_id"}`，`main.py:845-857`）。
- `users.user_key` / `project_members.role` 等新约束与既有 CHECK/UNIQUE 风格一致（`models.py:245-256`）。
- dbt 边身份 `source_ref="dbt:{P}=>{N}"` 满足 V0.9.2 的 `_TOKEN_PATTERN`（`schemas.py:177,181-183`）与 256 长度上限。
- review-context 复用函数的返回结构在 `main.py` 中均为已存在字典形状，无需序列化改造。
- OpenAPI JSON（`docs/v1.0/数据建模中心_V1.0_OpenAPI.json`）通过 JSON 合法性校验；风格与 `docs/v0.9/数据建模中心_V0.9.2_OpenAPI.json` 一致（3.1.0、components/schemas、FastAPI 生成风格）。
