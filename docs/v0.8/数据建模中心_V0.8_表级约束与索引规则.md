# 表级约束与索引设计规则 — V0.8

## 1. 目标

表级约束用于表达结构和数据完整性意图；索引用于表达查询访问路径意图。两者都归属于模型草稿，随正式发布快照冻结。逻辑元数据不保证目标引擎一定执行或支持相同语义。

## 2. 约束对象字段

`ModelConstraint` 主要字段：`model_id`、`constraint_name`、`constraint_type`、`field_codes_json`、`expression`、`referenced_model_id`、`referenced_field_codes_json`、`on_delete`、`description`。

| 类型 | 输入 | 服务端规则 | DDL / 生命周期 |
|---|---|---|---|
| `primary_key` | `field_codes` | 至少一个存在字段；字段不得重复；模型仅一个 PK；复合主键按字段顺序稳定 | 生成 PK constraint；参与发布快照；对应字段改为非空 |
| `unique` | `field_codes` | 至少一个存在字段；列顺序作为复合唯一定义；约束名模型内唯一 | 生成 UNIQUE；目标数据已有重复值时执行可能失败 |
| `check` | `expression` | token 白名单；引用字段必须存在；禁止分号、注释、任意函数调用和未知 token | 生成 CHECK 预览；不是完整 SQL parser，目标引擎仍需验证 |
| `foreign_key` | 本地字段、目标模型/字段、`on_delete` | 源/目标字段数量一致、字段存在、目标模型同项目；ON DELETE 采用白名单 | 生成外键预览；目标列通常需主键/唯一约束；Hive 仅作为逻辑元数据 |

### 2.1 复合主键示例

```json
{
  "constraint_name": "pk_tenant_order",
  "constraint_type": "primary_key",
  "field_codes": ["tenant_id", "order_id"],
  "description": "租户内订单唯一标识"
}
```

复合主键顺序应与业务键定义及索引访问路径一致。业务唯一键不必然是技术主键；如果存在稳定代理键，可以把自然键定义为 UNIQUE。

### 2.2 CHECK 表达式

允许的表达式片段按当前 token validator 定义，包含字段标识、数值/字符串字面量、比较/算术操作符和有限关键字（如 `AND`、`OR`、`NOT`、`IS NULL`、`IN`、`BETWEEN`、布尔常量等）。禁止：
- 分号、SQL 注释、未知字段、未经解析的 token；
- 任意函数调用、子查询、DDL/DML 片段；
- 将用户输入直接拼接进标识符或表名。

示例：`order_amount >= 0`。复杂业务规则应在业务规则/数据质量层实现，不要把有限 CHECK validator 当成完整 SQL parser。

### 2.3 外键语义

`on_delete` 当前白名单为 `NO ACTION`、`RESTRICT`、`CASCADE`、`SET NULL`（按 API 允许值使用）。如果使用 `SET NULL`，源字段必须允许为空。目标模型必须与源模型处于同项目。跨库/跨 schema 的外键、延迟约束、更新规则和复合目标索引高级语义不在当前范围内。

## 3. 索引对象字段

`ModelIndex` 主要字段：`model_id`、`index_name`、`index_type`、`field_codes_json`、`is_unique`、`description`。

- `field_codes` 必须非空、不得重复，字段顺序具有意义。
- 索引名在当前模型内唯一；与表级约束名冲突时应调整命名，避免 DDL 名称冲突。
- 索引键顺序应结合 `WHERE`、`JOIN`、`ORDER BY`、基数与选择性设计；不是每个字段都需要索引。
- 复合索引优先按查询谓词常用顺序设计并以查询计划验证，不应仅按表字段顺序自动建索引。
- 唯一索引要求现有数据满足唯一性；否则目标引擎创建会失败。

## 4. 当前引擎预览矩阵

| 能力 | PostgreSQL | MySQL | Hive |
|---|---|---|---|
| 普通 B-tree | 预览支持 | 预览支持 | 不生成通用物理索引 |
| Hash | 预览支持 | 通用预览拒绝 | 不生成 |
| GIN | 非唯一 GIN 预览支持 | 不支持 | 不支持 |
| UNIQUE + GIN | 明确拒绝 | 不支持 | 不支持 |
| PK / UNIQUE / CHECK / FK | 生成常见方言预览（CHECK/FK 需版本验证） | 生成常见方言预览（需版本验证） | 主要记录为逻辑元数据，不承诺引擎强制执行 |

上述矩阵描述的是当前生成器能力，不是完整数据库认证。schema、保留字、字符集、字段类型限制、最大索引长度、部分索引、表达式索引、前缀索引、操作符类等尚未完整建模。

## 5. 命名和版本规则

- 约束/索引名称使用 `[A-Za-z][A-Za-z0-9_]*` 风格并遵守目标引擎标识符长度限制；实际 adapter 应对超长名称策略化处理。
- 同一模型同类型对象的名称必须稳定、唯一；重命名应作为草稿变化进入版本差异。
- 发布快照包含约束、索引和该模型相邻关系；发布后不可直接修改历史版本。
- 删除约束/索引会产生变更记录；索引变更是性能风险，不应自动标记为业务语义改变。

## 6. 评审门禁建议

1. 复合 PK/UNIQUE：确认字段顺序、NULL 语义、业务唯一性和历史数据重复风险。
2. FK：确认源/目标字段数据类型兼容、字段数一致、目标唯一性、循环依赖和删除行为。
3. CHECK：确认表达式仅用于可由目标引擎执行的简单约束，并在目标版本测试。
4. 索引：记录查询场景、访问模式和预期收益；使用 `EXPLAIN`/目标引擎查询计划验证；审查写入和存储成本。
5. DDL：预览、解析、隔离 schema 执行和 catalog 校验全部通过后，才允许后续发布流水线考虑自动应用。
