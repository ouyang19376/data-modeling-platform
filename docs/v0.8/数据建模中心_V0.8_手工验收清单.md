# V0.8 手工验收清单

请在开发数据库副本上执行，逐项记录“通过/失败/不适用”、执行时间、版本、测试人及证据截图。当前浏览器 E2E 未由自动化执行，本清单需要本地操作验证。

## A. 数据库升级与既有数据

- [ ] 记录 V0.7 当前 revision，应为 `1b30fa87c419`。
- [ ] 备份后执行 `python -m alembic upgrade head`。
- [ ] `python -m alembic current` 输出 `4a8fc21d0e63`。
- [ ] `python -m alembic check` 无未迁移 schema 差异。
- [ ] 原有项目、需求、模型、字段、关系及发布版本记录数不减少。
- [ ] 连续启动两次没有重复建表或重复演示数据。

## B. 表级约束

- [ ] 创建一个复合主键（例如 `tenant_id + order_id`），保存后刷新仍然存在。
- [ ] 确认复合主键字段变为非空，且同一模型只能有一个主键约束。
- [ ] 创建单列和复合 UNIQUE，字段顺序保存一致。
- [ ] 创建 CHECK：`order_amount >= 0` 应通过。
- [ ] CHECK 包含分号、注释、未知字段、任意函数调用应拒绝并定位错误。
- [ ] 创建同项目外键，验证字段一一对应、目标字段存在和 ON DELETE 值校验。
- [ ] 跨项目外键、源/目标字段数量不一致、重复约束名应拒绝。
- [ ] 尝试对正式发布版本直接修改约束，应被拒绝；从正式版本发起变更后应允许修改草稿。

## C. 索引

- [ ] 创建 B-tree 索引并保持字段顺序。
- [ ] 创建复合索引并验证名称/类型/唯一标志/描述刷新后保留。
- [ ] 同模型重复索引名应拒绝。
- [ ] PostgreSQL unique GIN 组合应拒绝。
- [ ] MySQL Hash 通用预览应拒绝或明确提示未支持。
- [ ] 索引变化在版本差异中展示为索引变化，不被误判为字段变化。

## D. DDL 预览

- [ ] PostgreSQL：复合 PK、UNIQUE、CHECK、FK、B-tree/Hash/GIN（非唯一）预览按约定生成。
- [ ] MySQL：PK/UNIQUE/CHECK/FK/B-tree 预览符合目标版本要求，Hash 索引限制清楚。
- [ ] Hive：不宣称 PK/UNIQUE/CHECK/FK 被实际强制执行，不生成通用物理索引。
- [ ] DDL 接口只返回预览文本；确认不会连接目标引擎执行 SQL。
- [ ] 外键目标字段不具备 PK/UNIQUE 时显示风险，并在需要时阻止发布或执行。

## E. 模型图与影响分析

- [ ] 为同项目两个模型建立关系和字段映射，模型图展示正确节点、方向和字段。
- [ ] 未设置字段映射时，分析范围扩大到模型级并提示人工确认。
- [ ] 修改源字段后，映射命中的 target 字段被纳入候选影响。
- [ ] 删除/修改直接关系后，旧发布快照中的下游关系仍能被考虑。
- [ ] 设置较低 `max_nodes`，响应包含 `truncated=true` 或相应提示。
- [ ] 发生约束或关系变化时执行模型级分析；单纯索引变化不被当作业务语义变更。
- [ ] UI 提示“候选影响分析不是完整真实血缘”，并要求人工核验。

## F. 版本、并发和安全

- [ ] 发布 V1，发起变更并发布 V2；V1 的 `snapshot_json` 不发生变化。
- [ ] V2 版本差异能够识别新增/修改/删除约束与索引。
- [ ] 两个编辑会话保存同一模型时，旧 `edit_revision` 应产生冲突，而不是静默覆盖。
- [ ] 事件时间线存在约束/索引 CRUD、模型发布和影响分析关键事件（按当前实现范围）。
- [ ] 每个 API 响应包含 request ID；错误 body 和响应头的 ID 一致。
- [ ] `APP_ENV=production` / `staging` 被启动保护阻断。
