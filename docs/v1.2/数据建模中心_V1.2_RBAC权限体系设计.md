> 版本：V1.2 ｜ 主题：用户功能完善与权限/角色控制 ｜ 状态：已评审，作为实施依据
>
> 前置版本：V1.0（认证授权 M1/M2 已落地 api_key 认证 + 项目三角色 + 平台 admin 旁路）、
> V1.1（UI 改版）。本文只覆盖 V1.2 增量。

## 1. 背景：V1.0 已建成什么，还缺什么

### 1.1 既有能力（实施基线，不重构）

| 层 | 能力 | 落点 |
|---|---|---|
| 认证 | `AUTH_MODE=demo`（X-Actor 短路）/ `api_key`（Bearer `dmc_<key_id>_<secret>`，SHA-256 哈希存储、常量时间比较、缓存 TTL 60s + 吊销即时失效） | `backend/app/auth.py` |
| 平台级 | 单一角色 admin（`users.is_admin`），旁路全部项目级检查；一次性 bootstrap 开通首个 admin | `auth.py` / `POST /api/auth/bootstrap` |
| 项目级 | 三角色 owner/editor/viewer（`ROLE_LEVEL` 1/2/3），`require_project_role/require_model_role/require_requirement_role` 三个依赖工厂统一执行 | `auth.py` / `main.py` 各端点 |
| 凭据 | 密钥创建（secret 仅返回一次）/ 吊销 / admin 代建即开通（provisioning） | `POST/GET /api/auth/api-keys` |
| 成员 | 项目成员列表（viewer+）/ upsert 改角色（owner）/ 移除（owner，含最后一个 owner 保护） | `GET/POST/DELETE /api/projects/{id}/members` |

### 1.2 缺口（V1.2 要补的七项）

| # | 缺口 | 风险 |
|---|---|---|
| G1 | 用户无管理入口，主体只能经"admin 代建密钥"隐式开通 | 平台管理员无法盘点/停用主体，人员离职后凭据无法回收 |
| G2 | 无最后 admin 保护 | 最后一个 admin 被降级或禁用后平台锁死，只能改库 |
| G3 | 无自降级/自禁用防护 | admin 误操作把自己降级/禁用，同样锁死 |
| G4 | 成员 upsert 改角色无 last-owner 保护 | DELETE 路径有 `MEMBER_LAST_OWNER`，但 upsert 把唯一 owner 改成 viewer 可绕过保护，项目失去管理者 |
| G5 | 无有效权限查询端点 | 前端无法按权限显隐，只能猜；用户看不到"我有什么权限" |
| G6 | 前端零认证 UI | V1.0 明确"身份验证最后再做"，V1.2 补上 |
| G7 | 禁用用户时其存量密钥缓存不失效 | 依赖 TTL 60s 自然过期，禁用后最多 60s 内旧令牌仍可用 |

## 2. 权限模型：两级 RBAC

### 2.1 总体结构

```
平台级（全局，唯一角色 admin）
  └─ 用户生命周期管理、代建密钥、观测端点 /metrics
  └─ 旁路全部项目级检查（既有语义，保留）

项目级（每项目独立授权，三角色）
  ├─ owner  —— 项目内全权 + 成员管理
  ├─ editor —— 模型/字段/需求/关系/评审发布
  └─ viewer —— 只读 + 校验/DDL/差异等派生视图
```

设计原则：

1. **两级正交**：平台级管"人"，项目级管"事"。admin 是运维角色而非业务角色——它管理主体与凭据，业务操作仍走项目角色（旁路仅为运维便利，语义上等价于"所有项目隐式 owner"，该语义 V1.0 已确立，V1.2 不改）。
2. **最小权限**：默认非 admin；密钥代建是唯一的自助开通路径（provisioning），创建即最低权限（无任何项目成员关系），后续由项目 owner 按需授权。
3. **集中式矩阵**：角色→动作的映射集中在一处声明（见 2.3），端点通过依赖工厂消费，前端通过 `/api/auth/me` 的 capabilities 消费同一矩阵，杜绝前后端各写一套。

### 2.2 项目级权限矩阵（现状固化 + 显式化）

| 动作族 | 具体端点 | viewer | editor | owner | 备注 |
|---|---|:-:|:-:|:-:|---|
| 项目元数据查看 | GET /api/projects、/api/projects/{id} | ✓ | ✓ | ✓ | |
| 模型/字段/需求/关系查看 | GET 各资源 | ✓ | ✓ | ✓ | |
| 派生视图 | /validate、/ddl、/versions、/diff、/graph、/impact、/lineage | ✓ | ✓ | ✓ | 只读派生，不降级给 viewer 无收益 |
| 模型/字段 CRUD | POST/PUT/DELETE models、fields、constraints、indexes | ✗ | ✓ | ✓ | |
| 需求/关系 CRUD | POST/PUT/DELETE requirements、relationships | ✗ | ✓ | ✓ | |
| 主题域 CRUD | subject-areas | ✗ | ✓ | ✓ | |
| 评审发布 | submit-review、approve、publish、reject、activate/deactivate | ✗ | ✓ | ✓ | |
| 图谱快照/血缘导入 | snapshots、lineage import 族 | ✗ | ✓ | ✓ | |
| 成员查看 | GET members | ✓ | ✓ | ✓ | |
| 成员管理 | POST/DELETE members | ✗ | ✗ | ✓ | owner 专属 |
| 观测指标 | GET /metrics | ✗ | ✗ | ✗ | admin 专属（平台级） |
| 他人密钥代建/查询 | POST api-keys(user_key)、GET api-keys?user_key | ✗ | ✗ | ✗ | admin 专属（平台级） |

> 本矩阵与 V1.0 实施完全一致——V1.2 做的是**把它显式落成代码里的单一事实源**，供依赖工厂与 capabilities 共用，行为零变化。

### 2.3 平台级权限矩阵（V1.2 新增显式化）

| 能力（capability） | 说明 | 拥有者 |
|---|---|---|
| `user.manage` | 用户列表/创建/改角色/禁用启用 | admin |
| `api_key.provision` | 为他人代建密钥、查他人密钥 | admin |
| `metrics.view` | 查看 /metrics | admin |
| `member.manage` | 项目成员管理（按项目） | 该项目 owner、admin |
| `model.write` | 项目内写操作（按项目） | editor、owner、admin |
| `model.read` | 项目内读操作（按项目） | viewer+、admin |

### 2.4 防护规则（不变量清单）

| # | 规则 | 触发点 | 错误码 |
|---|---|---|---|
| P1 | **最后 admin 保护**：禁止把最后一个 active admin 降级（`is_admin: true→false`）或禁用（`status: active→disabled`） | `PUT /api/users/{id}` | 409 `ADMIN_LAST_ADMIN` |
| P2 | **禁自降级**：admin 不能取消自己的 admin 身份（防止误锁；要降级须由另一 admin 操作） | `PUT /api/users/{id}` | 409 `ADMIN_SELF_DEMOTE` |
| P3 | **禁自禁用**：admin 不能禁用自己 | `PUT /api/users/{id}` | 409 `ADMIN_SELF_DISABLE` |
| P4 | **成员 upsert last-owner 保护**：upsert 把项目唯一 owner 改成低角色 → 拒绝（与 DELETE 路径对齐） | `POST /api/projects/{id}/members` | 409 `MEMBER_LAST_OWNER` |
| P5 | 禁用主体不可被加成员、不可发密钥（V1.0 已有 `USER_DISABLED` 409，保留） | members upsert / api-keys 创建 | 409 `USER_DISABLED` |
| P6 | **禁用即时全量失效**：用户被禁用时，invalidate 其全部密钥缓存，不等 TTL | `PUT /api/users/{id}`（status→disabled） | — |
| P7 | 管理端点一律 `require_admin`，非 admin 一律 403 `ADMIN_REQUIRED`（demo 模式短路，见 4.4） | 全部 /api/users | 403 `ADMIN_REQUIRED` |
| P8 | secret 仅创建响应返回一次（V1.0 已有，保留） | api-keys 创建 | — |

规则间优先级：P1 先于 P2/P3 判定（最后一个 admin 时任何降级/禁用都先撞 LAST_ADMIN，错误信息更准确）。

### 2.5 自锁逃生舱（明确不做的事）

不提供"重置 admin"的后门端点。锁死场景（所有 admin 都丢了）恢复路径：停服务 → 直接改库 `users.is_admin` → 重启。这是有意的：任何可远程调用的逃生舱都是攻击面。文档中明示该路径即可。

## 3. 有效权限查询：`GET /api/auth/me` 增强

前端"按权限显隐"与用户"我的权限"自解释都依赖此端点。V1.2 在既有返回（身份 + projects）基础上补 `status` 与 `capabilities`：

```json
{
  "user_key": "u:demo.admin",
  "display_name": "演示管理员",
  "kind": "human",
  "auth_mode": "demo",
  "is_admin": true,
  "status": "active",
  "capabilities": {
    "platform": ["user.manage", "api_key.provision", "metrics.view"],
    "projects": [
      {"project_id": 1, "role": "owner",
       "capabilities": ["model.read", "model.write", "member.manage"]}
    ]
  },
  "projects": [ ... 既有字段不动 ... ]
}
```

- `platform` 由 `is_admin` 推导（单一事实源 = 平台矩阵 2.3）；
- `projects[].capabilities` 由 `role` 推导（项目矩阵 2.2 的粗粒度能力族，不含逐端点明细——前端显隐只需要能力族粒度）；
- admin 的 projects 列表仍只含显式成员关系（旁路是认证期语义，不虚构成员行），但其 capabilities 含全部能力族。

## 4. API 设计（V1.2 增量）

### 4.1 用户管理（admin，`require_admin`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/users` | 用户列表；查询参数 `status`（active/disabled）、`q`（user_key/display_name 模糊）；每项含 `project_count`、`active_key_count` 摘要 |
| POST | `/api/users` | 创建主体；body `{user_key, display_name, kind, is_admin}`；`user_key` 重复 → 409 `USER_KEY_EXISTS`；写审计 `user.created` |
| PUT | `/api/users/{user_id}` | 更新；body `{display_name?, is_admin?, status?}` 至少一项；防护 P1/P2/P3/P6；写审计 `user.updated` / `admin.granted` / `admin.revoked` / `user.disabled` / `user.enabled` |

说明：

- **创建即发凭据**是 provisioning 语义（V1.0 代建密钥），V1.2 把它拆成两步：`POST /api/users` 管"人"，`POST /api/auth/api-keys`（带 user_key）管"凭据"。职责单一，也满足"先建人后授权"的组织流程。
- `kind` 仅创建时可指定（human/service_account），之后不可改（账号类型是身份属性）。
- `status` 用显式 `active`/`disabled` 枚举，不做删除（审计与成员关系都引用 user_id，物理删除会断引用；SQLAlchemy 层 ProjectMember/ApiKey 虽 ON DELETE CASCADE，但 AuditLog 的 object_id 是字符串快照，删用户会丢追溯）。

### 4.2 成员 upsert 防护（P4）

`upsert_project_member_endpoint` 在调用 `upsert_project_member` 前：若目标成员已存在且当前角色为 owner、新角色低于 owner、且该项目 owner 数 ≤ 1 → 409 `MEMBER_LAST_OWNER`。与 DELETE 路径同一错误码，前端可统一提示"请先移交项目所有权"。

### 4.3 禁用联动（P6）

`PUT /api/users/{id}` 使 `status → disabled` 时，对该用户全部 `active` 密钥执行 `key_cache.invalidate`（revoke 已内置，此处直接复用）。下一请求即 401/403，不依赖 TTL。

### 4.4 demo 模式行为

`require_admin` 与既有依赖工厂一致：`AUTH_MODE=demo` 下短路返回，`/api/auth/me` 回落演示管理员（is_admin=true）。即演示模式下用户管理界面完全可用——演示的是"功能形态"，生产模式（api_key）下才是真实权限。前端在 demo 模式显示常驻横幅说明。

### 4.5 错误码表（V1.2 新增）

| 错误码 | HTTP | 场景 |
|---|---|---|
| `ADMIN_REQUIRED` | 403 | 非 admin 访问 /api/users |
| `USER_KEY_EXISTS` | 409 | 创建用户时 user_key 重复 |
| `ADMIN_LAST_ADMIN` | 409 | 最后一个 admin 被降级/禁用 |
| `ADMIN_SELF_DEMOTE` | 409 | admin 自降级 |
| `ADMIN_SELF_DISABLE` | 409 | admin 自禁用 |
| `MEMBER_LAST_OWNER` | 409 | upsert 降级项目唯一 owner（V1.0 已有，场景扩展） |

## 5. 前端设计（"用户与权限"视图）

新增导航项 **用户与权限**（仅 `capabilities.platform` 含 `user.manage` 时可见；非 admin 点击引导文案"仅平台管理员可管理用户"）。视图内四张卡，全部按能力显隐：

1. **当前身份卡**（所有人可见）：user_key、display_name、kind、admin 徽标、auth_mode、平台能力徽标 + 本人项目角色表（来自 `/api/auth/me`）。
2. **用户管理卡**（`user.manage`）：用户表（user_key/名称/类型/admin/状态/项目数/密钥数/创建时间）+ 筛选（状态、关键词）+ 新建按钮 + 行内操作（改角色/禁用启用）。禁用/降级按钮对"最后一个 admin"与"自己"置灰并 tooltip 说明（与服务端 P1-P3 双重防护，前端只是体验）。
3. **项目成员卡**（当前项目 owner 或 admin）：当前项目成员表 + 添加成员（user_key + 角色下拉）+ 改角色 + 移除；复用 `GET/POST/DELETE /api/projects/{id}/members`。最后一个 owner 行禁用移除/降级。
4. **API Key 卡**（所有人）：本人密钥列表（名称/key_id/状态/创建时间/最近使用/过期）+ 创建（名称 + 有效期天数）+ 吊销；admin 额外显示"为他人代建"输入框（user_key）。secret 仅在创建响应弹窗展示一次 + 复制按钮。

交互红线（延续 V1.1 E2E 约定）：既有 class/id 一律不动；新视图独立命名空间（`#view-users` 等）。

### 6.1 测试矩阵（pytest 新增，沿用 `_v10_*` 模式）

- **正向**：admin 建用户/改角色/禁用/启用；owner 管理成员；capabilities 推导正确。
- **越权**：editor/viewer 访问 /api/users → 403 ADMIN_REQUIRED；非 owner 改成员 → 403 PROJECT_ROLE_INSUFFICIENT。
- **锁死防护**：P1（最后 admin 降级/禁用）、P2（自降级）、P3（自禁用）、P4（upsert 降唯一 owner）。
- **即时失效**：禁用后旧令牌下一请求即被拒（P6/P7）。
- **回归**：V1.0 既有认证/成员测试全绿。

## 7. 明确不在本版范围

- OIDC/LDAP 外部身份源（`auth_source` 列已预留，V1.3+ 再接）；
- 自定义角色/细到字段级的权限（当前三角色 + 能力族粒度已覆盖建模中心规模；真出现需求时，矩阵集中在 2.2/2.3 一处扩展）；
- 密钥轮换策略（轮换 = 建新 + 吊销旧，现有端点已可组合完成）。
